# Script: scratchpad/510-518-measure.mjs, unchanged method (page clock).

#   base 99bafe8: runs=[721, 725, 1110, 816, 730, 730, 716, 726, 759, 753]      median=730ms  p90=816ms

#   head is +358 ms slower (median), about 2 RTT at 156-163 ms each

# create-to-Lobby x5 (click "Create session" -> first participant in the DOM)
#   base 99bafe8: runs=[2561, 1485, 1717, 2030, 1386]  median=1717ms p90=2561ms
#   head aefe386: runs=[1255, 1081, 1109, 1089, 1088]  median=1089ms p90=1255ms   (head faster)
#
# Where the reload time goes (DIAG=1 reload 3, page clock ms from navigation start):
#   base: first polling GET +14..+25 on the page's already-open HTTP/2 connection to the backend;
#         socket connect (Engine.IO "40" received) at +351..+450 = 2 RTT; participant +732..+831
#   head: new WebSocket() at +11..+12; ws open +504..+574 (fresh TCP + TLS + HTTP/1.1 Upgrade = 3 RTT);
#         connect +675..+747 (+1 RTT for the Socket.IO "40" exchange); participant +1125..+1179
# Cause: on a reload, polling rides the connection that is already open, while a WebSocket
# needs its own new connection (TCP + TLS + Upgrade) before the Socket.IO connect. That is +2 RTT
# before RequireSession lets the page fetch its Session. transports: ['websocket'] is what the reload pays for.
# Note: Playwright's page 'websocket' event (the "websocket requests +NNNms" lines in the waterfall/reload
# output) fires ~2 RTT after new WebSocket(), i.e. at the handshake request, not at construction.
