# How can Coles product, price and aisle data be obtained?

Research for issue #227 (parent map: #225 — cook-branch shopping list pricing). The cook branch needs, per ingredient: a matching product's name, pack size, price, a deep link, and ideally an aisle number — obtained without holding Coles credentials or automating a basket. This document chases every route to that data against primary sources: Coles' own site, Apify's actual store listings, reverse-engineered API repos, and the relevant Terms of Use.

## 1. Official / affiliate route

**No data-licensing or developer API programme exists.** Coles does not run a public developer portal or product/price data-licensing programme. A 2021-era community note observes plainly that "Coles didn't have a public API, whereas Woolworths did" — and nothing found in this research contradicts that for 2026; Woolworths' own [API Catalogue](https://apiportal.woolworths.com.au/) is B2B supply-chain (TMS/WMS/vendor systems), not a consumer product/price feed either, so it wouldn't have helped even if Coles had an equivalent.

**Coles does run a commission affiliate programme, but it grants no data access.** Coles Online is listed on Impact.com (surfaced via the aggregator directory [affi.io/m/coles-online](https://affi.io/m/coles-online)): a standard "publisher drives a click, Coles pays a commission on the resulting purchase" arrangement ("Collect flybuys as you shop"), with no commission rate or cookie duration published on the public listing. This is a traffic-referral programme, not an API or feed — it would let Dinder link to Coles and earn a cut if a user buys, but it returns zero product/price/aisle data and doesn't solve the actual problem (matching an ingredient to a priced product).

**Coles360 / Cartology are advertising, not data licensing.** [Coles 360](https://www.coles.com.au/coles360/360-media-connections) is Coles' retail-media arm (in-store screens, sponsored placements, a bespoke planning tool built with Nielsen) — it sells ad inventory to brands, it does not sell product/price data to third-party apps.

**Licensed data vendors don't cover this use case.** Nielsen and Quantium are the two names that actually touch Australian grocery data commercially, and both are Woolworths-side, not Coles: Nielsen is Woolworths' "scan market read and consumer panel provider of choice" ([nielsen.com](https://www.nielsen.com/au/en/news-center/2018/woolworths-selects-nielsen-data-provider-choice-australia/)); Quantium is Woolworths Group's 80%-owned data/AI analytics subsidiary selling supplier-facing sales analytics, not a per-SKU retail price feed a consumer app could subscribe to. Neither publishes a Coles product/price API. A search across Awin, CJ Affiliate and Impact.com for a Coles data or affiliate listing (beyond the commission programme above) returned nothing relevant to product data.

**Conclusion:** searched — coles.com.au corporate/footer pages, Coles Group investor materials (implicitly, via the absence of any developer/API page), Coles360/Cartology, Awin/CJ/Impact affiliate networks, Nielsen/Quantium/RapidAPI-style vendors. Nothing exists that both (a) grants product/price/aisle data and (b) is commercially licensable. This branch is a dead end for v1.

## 2. Unofficial APIs

The Coles Online web/app client calls a real JSON backend, and it has been reverse-engineered publicly. [drkno/au-supermarket-apis](https://github.com/drkno/au-supermarket-apis) — OpenAPI specs "reverse engineered from respective mobile apps and web clients" — documents the host as **`https://apigw.coles.com.au/digital/colesappbff`** (with matching non-prod hosts `apigwsvt1`/`apigwtest2`/`apigwdev2`), and the key endpoint as **`GET /v2/products/search`**, taking `searchTerm`, `storeId`, `start`, `limit`. Adjacent endpoints: `/v2/products/search/suggestions` (autocomplete), `/v2/products/category/{categoryId}`, a product-by-SKU/barcode lookup, and a `boughtBefore` endpoint. The spec itself doesn't carry full response-body schemas (`content: {}` in most response definitions), so the exact JSON shape has to come from scraper projects that actually parse it.

Those projects confirm the fields needed exist: [abhinav-pandey29/coles-scraper](https://github.com/abhinav-pandey29/coles-scraper) extracts product name, brand, **price** (e.g. `"$0.68"`), **unit pricing** (e.g. `"$4.00 per 1kg"`), product URL, retail/promo limits, product codes and category breadcrumbs — i.e. pack size and unit price are present. [tjhowse/aus_grocery_price_database](https://github.com/tjhowse/aus_grocery_price_database) corroborates a simpler shape ("There is always a SKU ID, product name, department ID/name and price" — noting Coles, unlike Woolworths, doesn't expose a barcode field).

Stability/rate-limiting: the coles-scraper repo ships a `ColesPageFetcher` explicitly described as handling "automatic cookie refresh and bot detection handling" — i.e. Coles does run bot detection against this traffic and the scraper has to manage session cookies to survive it. Its own README carries the honest disclaimer: *"This is a hobby project for my personal portfolio. Please scrape responsibly and adhere to website terms of service."* No maintainer publishes an uptime/breakage SLA (unsurprising — it's an unofficial reverse-engineered surface); the general pattern for this class of endpoint (also true of DoorDash/Uber Eats per ADR 0004) is that it works until Coles changes something, with no warning and no vendor to escalate to.

Citations: [au-supermarket-apis/coles.yaml](https://github.com/drkno/au-supermarket-apis/blob/main/coles.yaml) · [abhinav-pandey29/coles-scraper](https://github.com/abhinav-pandey29/coles-scraper) · [tjhowse/aus_grocery_price_database](https://github.com/tjhowse/aus_grocery_price_database)

## 3. Apify actors

Two Coles-specific actors and one Woolworths actor were found and read directly on the Apify Store:

**[Coles Product Search Scraper](https://apify.com/stealth_mode/coles-product-search-scraper)** (owner: `stealth_mode`, community; 99 total / 16 monthly users, 98.4% run success). Input: search-result-page `urls`, `max_items_per_url`, `ignore_url_failures`, `proxy`. Output per product: id, name, brand, description, **size**, availability/quantity, image URIs, a **`pricing`** object (current price, unit pricing, promo pricing, currency), a **`locations`** array with an **`aisle`** field, merchandise-hierarchy/category taxonomy, purchase restrictions, ad/promo flags. Confirmed present: pack size, price, unit price, category. **Not present: a direct product-page URL** — the output carries `from_url` (the search page scraped), not a per-product deep link, which is a gap against what issue #227 needs (see recommendation). Pricing: **pay-per-event, $2.80 per 1,000 results**, discounted at higher Apify subscription tiers.

**[Colesau Product Spider](https://apify.com/getdataforme/colesau-product-spider)** (owner: `getdataforme`; 14 total / 1 monthly users, 100% success) — a narrower per-product-page scraper. Extracts name, description, SKU, price, currency, images, brand, offers — but pack size, unit price and aisle/category are not documented as extracted fields. Pricing: **$9.00 per 1,000 results**, more expensive and less complete than the `stealth_mode` actor.

**[Woolworths AU Product Search & Catalog (unofficial)](https://apify.com/dromb/woolworths-au-product-search-catalog-unofficial)**, for comparison — four operations (search/item/category/categories), returns id/sku/barcode/name/brand/slug, price + discount price + parsed unit-price attributes, size/unit, image, source_url (a real product URL, unlike the Coles actor), and category breadcrumbs. Pricing: **from $0.30 per 1,000 results**, cheaper again.

Apify's own platform tiers (baseline compute-unit economics, from [apify.com/pricing](https://apify.com/pricing)): **Free** — $0/mo, $5/mo usage credit, overage $0.20/CU; **Starter** — $29/mo, $29 credit, $0.20/CU; **Scale** — $199/mo, $199 credit, $0.16/CU; **Business** — $999/mo, $999 credit, $0.13/CU. Pay-per-event actor pricing (like the $2.80/1,000-results Coles actor) is billed against this same platform credit, so the Free tier's $5/month already buys real usage before any paid plan is needed.

## 4. Aisle numbers

**Nuanced finding, not a clean "no."** The `stealth_mode` Coles actor's output does carry a `locations` array with an `aisle` field, e.g.:

```json
"locations": [{
  "aisle_side": "Front of Store",
  "description": "Located in Fresh produce at $STORE",
  "facing": 0,
  "aisle": "Fresh produce",
  "order": 0,
  "shelf": null
}]
```

Two things matter here. First, `aisle` is a **coarse section/category name** ("Fresh produce"), not a numbered aisle ("Aisle 7") — it's planogram-section data, not the kind of precise "walk to aisle 7" number the official app's in-store navigation shows. Second, the literal `$STORE` left in the `description` template string, plus the underlying `/v2/products/search` endpoint requiring a `storeId` parameter (confirmed in [au-supermarket-apis/coles.yaml](https://github.com/drkno/au-supermarket-apis/blob/main/coles.yaml)), means this location data is **keyed to one specific physical store** — it isn't a store-agnostic "this product lives in the produce section everywhere" fact, it's "at store #X, this product is in this section." To get it for a real store you'd need that store's numeric ID, and no store-lookup/nearby-stores endpoint was found documented anywhere in the reverse-engineering repos searched (the site's own `/store-locator/` path is separately disallowed for crawling per `robots.txt`, see §5).

The genuinely precise, numbered-aisle "walk me to it" feature — the one Coles markets — is the **in-app "Shopping List" / in-store mode**, which sorts a user's list by aisle once they've set their home store in the Coles app (confirmed via Coles' own app help content and user how-tos, not just a blog claim: [coles.com.au/about/coles-app](https://www.coles.com.au/about/coles-app), [Coles app FAQ](https://app.coles.com.au/information/faq)). That feature is tied to the official first-party app and a selected store; it is not exposed as a queryable external field beyond the coarse section-level `aisle` string above.

**Bottom line for Dinder:** a numbered, store-precise aisle is only ever inside the official Coles app tied to a selected physical store. What leaks through the same unofficial-API/Apify channel already used for price is a coarse category/section label, itself tied to a specific storeId that Dinder has no documented way to resolve from a suburb/postcode without further reverse-engineering. Treat aisle as **not reliably available** for v1; a "which section" hint (produce/dairy/pantry) is a maybe-later nice-to-have, not a v1 commitment.

## 5. Terms of service exposure

Coles' own [Website Terms and Conditions](https://www.coles.com.au/important-information/terms/website-terms-conditions) are explicit and restrictive, quoted directly:

- **Personal use only, in writing:** *"You may only use the Website and the Content on the Website for personal purposes unless Coles provides express written consent."*
- **No republication/automation implied by the copy/distribute clause:** *"copy, reproduce, republish, adapt, upload, link, post, frame, translate, transmit or distribute any part of the Website"* is prohibited.
- **Explicit anti-load clause** (closest thing to an anti-scraping clause): *"impose an unreasonable or disproportionately large load on the Website, or interferes or disrupts"* it is prohibited. There is no separate clause naming "bots," "crawlers," or "scraping" by name, but the personal-use-only clause alone is sufficient to make any commercial, automated use of Coles.com.au data a Terms breach.
- **IP ownership:** *"All copyright, data, text, software, images, graphics, trademarks, logos... is owned, controlled by, or licensed to Coles"*, with usage rights limited to *"viewing the Content for your own personal non-commercial use."*
- **robots.txt** (fetched directly from `coles.com.au/robots.txt`) disallows `/search/`, `/store-locator/`, `/account/`, `/lists/`, `/brand/*`, `/checkout/*`, `/auth/*`, and tracking-parameter URLs, and disallows `/product/*$` while allowing `/product/*-*` — i.e. Coles' own robots directives already tell crawlers to stay off search and store-locator pages, though robots.txt is a courtesy convention, not a legal instrument on its own; the Terms of Use is the actual contract being broken.

**Apify's Terms** ([docs.apify.com/legal/general-terms-and-conditions](https://docs.apify.com/legal/general-terms-and-conditions)) push responsibility onto the user, not Apify: *"You are solely responsible for the legality, accuracy, quality, appropriateness, and use of all Customer Data"*; users must "process only the Customer Data that you are authorized to access and that is in compliance with all applicable laws"; users must indemnify Apify against *"any third-party claim, liability, loss, and expense... arising out of... your use of the Website or Services in breach of the Agreement"*. Apify disclaims control over "Third-Party Services" but doesn't specifically warrant that any actor's target site permits scraping. In short: Apify's ToS puts the legal exposure of scraping Coles squarely on whoever runs the actor (Dinder), not on Apify or the actor's community author.

**Honest posture, stated plainly, three routes:**
1. **Official/affiliate** — clean. No exposure, because there's nothing to license (see §1) beyond the irrelevant commission programme.
2. **Direct unofficial API call from Dinder's own backend** — a clear breach of Coles' personal-use-only Terms of Use the moment it's automated and/or used commercially, identical in kind to ADR 0004's assessment of scraping DoorDash's AU site ("Acceptable at personal/hobby scale; revisit with legal advice before any public launch at scale").
3. **Apify actor** — the same underlying ToS breach, one layer removed: Dinder isn't the one issuing the HTTP requests, but Dinder is still the one directing them and consuming the result, and Apify's own terms make clear that doesn't shift legal responsibility away from the operator. This is the **exact same risk class Dinder already accepted for DoorDash and Uber Eats in ADR 0004** — not a new or larger risk, just the same one applied to a third target site.

## 6. Per-unit cost

**(a) Apify actor route.** Using the `stealth_mode` Coles actor at **$2.80 / 1,000 results**: to price a ~12-ingredient shopping list, Dinder doesn't need all 20 results per search — enough to find a confident match, say ~8 results/ingredient. 12 × 8 = 96 results ≈ **$0.27 per shopping list, cold** (no cache at all). Apify's Free plan's $5/month credit alone covers roughly 1,785 results/month — about **18 full cold shopping lists a month before spending a cent beyond the free tier**, and Starter ($29/mo) covers ~10,357 results (~860 cold lists/month) if usage grows past free-tier.

**(b) Direct unofficial API.** Calling `apigw.coles.com.au/digital/colesappbff/v2/products/search` from Dinder's own backend has near-zero marginal dollar cost (just Dinder's own compute/bandwidth) — but the engineering cost is real and ongoing: cookie/session management to survive Coles' bot detection (per §2), no vendor SLA, and breakage with zero notice when Coles changes the endpoint, since there's no maintainer to watch for it but Dinder itself.

**Shared caching is what actually matters, and it's a bigger lever here than for restaurant delivery.** ADR 0004/0005's Snapshot cache exists because DoorDash/Uber Eats prices are *per-venue, per-location* — a Melbourne storefront's menu doesn't help a Sydney user, so cache reuse is bounded by geography. Coles online prices are **effectively national**, not per-suburb: a can of chickpeas has essentially one price regardless of which two users are cooking with it. That means the natural cache key for Coles data is **product/SKU**, not **product × location × user**, so cache hit rate compounds much faster than the delivery-price case as user count grows.

Worked example: suppose Dinder's cook branch draws from a shared vocabulary of roughly **800 distinct grocery staple products** across its recipe catalog (onion, garlic, olive oil, canned tomatoes, chicken breast, pasta, etc. recur constantly across recipes — the ingredient vocabulary is far smaller than the recipe count). Even at **5,000 shopping lists generated in a month** (12 ingredients each = 60,000 ingredient-lookups), the number of *fresh* Apify lookups needed is bounded by the *distinct products encountered*, not the *lists generated* — because every lookup after the first hit for a given product within its cache TTL is a Redis hit costing ~$0. With a same-order-of-magnitude TTL to ADR 0005's 6h/2min pattern (say, refresh each cached product once every 24–48h, since grocery prices don't move intraday), keeping the entire 800-product vocabulary warm costs roughly 800 products × ~8 results ≈ 6,400 Apify results per refresh cycle ≈ **$17.92/day worst case, or ~$0.27–0.90/day realistically** (most refresh cycles are hit-driven, not a full sweep) — i.e. **well under $30/month app-wide** to keep pricing fresh for an arbitrary number of users, because the cost scales with *how many distinct products Dinder's recipes touch*, not with *how many people are cooking*. Per-user marginal cost trends toward zero as usage grows, which is exactly the architectural requirement from #225: two nearby users cooking the same dish cost about one lookup between them — and at national-price granularity, that's actually two *arbitrarily located* users, not just two in the same suburb.

## Recommendation

**Use the Apify `stealth_mode/coles-product-search-scraper` actor, behind a single client module, with a national product-keyed Redis cache — the same shape ADR 0004 already established, applied to a cheaper, higher-hit-rate case.** No better route exists: §1 turned up no licensable affiliate/data programme (Coles' actual affiliate listing is a traffic-commission deal with zero data access), and no AU grocery-price vendor (Nielsen/Quantium) sells anything usable or Coles-side. The direct-unofficial-API route (§2) carries the identical legal exposure as the Apify actor (§5) for near-zero dollar savings, but trades that for real, ongoing engineering cost (bot-detection/cookie maintenance with no vendor to lean on) — worse on every axis except marginal $, which the caching math in §6 already makes irrelevant.

Concretely for cook-branch v1:
- **Data source:** the `stealth_mode` Coles actor (pack size, price, unit price, category all confirmed present); accept that it does **not** return a direct product-page URL — Dinder will need to construct/resolve the deep link itself (e.g. from product ID/slug against `coles.com.au/product/...` conventions) or supplement with a second, cheap lookup; flag this as a follow-up spike, not a blocker.
- **Aisle:** don't commit to it in v1. What's available (§4) is a coarse, store-specific section label requiring a storeId Dinder has no clean way to resolve — ship without aisle, revisit only if a store-ID resolution path turns up later.
- **Caching:** cache by product/SKU nationally (not per-user, not per-suburb) with a ~24–48h TTL, mirroring ADR 0005's Snapshot pattern — this is what makes the whole route cheap at scale, and per the architectural requirement it must be shared cache from day one, not bolted on later.
- **Legal posture:** identical risk class to ADR 0004's DoorDash/Uber Eats decision — acceptable now, revisit with legal advice before scaling past hobby/personal use, and treat the actor ID as swappable config exactly as ADR 0004 already prescribes, since this is one more maintainer-run Apify actor subject to the same churn/delisting risk.
