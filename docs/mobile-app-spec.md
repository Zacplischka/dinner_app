## Problem Statement

People can currently use Dinder, being rebranded as Heykeen, through a browser, but cannot install an officially distributed Android or iPhone app. Existing browser behavior does not yet establish reliable recovery after a phone terminates the app, store-compatible sign-in, verified app-opening Invite Links, or the privacy and safety controls needed for distribution.

The product depends on a whole group being able to participate. Requiring every invited person to install an app or create a Profile would undermine its existing value. Installation must therefore improve convenience for regular Participants while preserving browser participation, guests, and the same shared Session across devices.

## Solution

Release a free, Australia-first app through Google Play and Apple's App Store using the existing React frontend packaged with Capacitor. Keep the browser application and existing backend. Support the Eat Out, Takeaway, Cook and Watch Branches, optional Profiles and Friends, Shopping Lists, Cook View, Comparison and Group Order handoffs.

An installed app opens an Invite Link into the correct Session; someone without it joins in a browser. Participants can switch applications, lock their phones and recover a still-valid Session without becoming a second Participant. Location and sharing work naturally on each platform. Profile holders can authenticate, manage their connections and delete their accounts. The operator can build, test, support and update both apps without breaking older installed clients.

Validate this approach with a small physical-device prototype before the rest of the migration. Success means a reliable, accessible, store-reviewable product with verified mixed-device behavior, rather than merely generating native project files.

## User Stories

1. As a person in Australia, I want to install the app from Google Play, so that I can find and open it like my other Android apps.
2. As a person in Australia, I want to install the app from Apple's App Store, so that I can use it on my iPhone.
3. As a returning Participant, I want consistent branding in the store, app and website, so that I know I have found the same product.
4. As a guest, I want to create or join a Session without a Profile, so that I can decide with my group immediately.
5. As an invited guest, I want to join through a browser without downloading, so that I do not hold up the group.
6. As a Host, I want iPhone, Android and browser Participants in the same Session, so that device choice does not divide the group.
7. As a Host, I want to create a Session in any of the four existing Branches, so that installation does not remove a current use case.
8. As a Participant, I want to contribute interests in the Lobby and confirm Ready, so that the shared Deck reflects the group's choices.
9. As a Participant, I want changing my choices to clear my Ready state, so that the Host cannot start using my previous confirmation.
10. As a Participant with Dietary Requirements, I want the Cook Deck to respect them and handle conflicting late arrivals, so that mobile preserves the existing dietary rules.
11. As a Participant, I want the same fixed Deck as everyone else in the round, so that our Selections remain comparable.
12. As a Participant, I want to Like, Pass and Undo through usable controls, so that I can choose without relying on a swipe gesture.
13. As a Participant, I want an empty Submission to count as finished, so that passing on everything does not prevent completion.
14. As a Participant, I want the Match and Top Pick to retain their existing meanings, so that a fallback choice is never presented as unanimous agreement.
15. As a Host, I want to share an Invite Link through my phone's share sheet, so that I can invite my group using an application I already use.
16. As a Host, I want a copyable Invite Link and Session Code when sharing is unavailable, so that I can still invite someone.
17. As a Host, I want dismissing the share sheet to leave my Session alone, so that cancellation is harmless.
18. As an invite recipient with the app installed, I want the link to open the correct Session from either a closed or open app, so that I do not have to find it manually.
19. As an invite recipient without the app, I want the browser to retain the Session Code, so that I can join immediately.
20. As a person installing after receiving an invite, I want clear guidance to reopen the original link or enter its code, so that I am not promised an unreliable transfer through installation.
21. As a Participant already in a Session, I want deliberate handling before joining another, so that opening a link does not unexpectedly discard my current participation.
22. As a recipient of an old or invalid Invite Link, I want an honest error and a route back to joining or creating, so that I understand why it cannot be used.
23. As a returning Participant, I want app termination and reopening to recover my valid identity and progress, so that I do not displace myself or another Participant.
24. As a Participant on an unreliable connection, I want useful reconnect status and retry behavior, so that a temporary outage does not erase recoverable work.
25. As a Participant returning after Restart, I want the current round to replace stale progress, so that old Selections cannot affect the new Deck.
26. As a Participant whose Session expired, I want the app to clear obsolete recovery state, so that it does not revive old participation or enter a different Session with a reused code.
27. As a Participant leaving deliberately, I want Leave to remove me and clear my recovery capability, so that reopening does not silently rejoin me.
28. As a Host, I want Disconnect and Leave to retain different behavior, so that a briefly offline Participant still has their place.
29. As a Participant who sees a timed-out action, I want the app to reconcile server state before repeating it, so that an unknown outcome does not become a duplicate mutation.
30. As a person offline, I want the installed interface to open with a clear connectivity message, so that I know which actions need a connection.
31. As a person searching nearby, I want location access requested only when I choose it, so that the permission has an obvious purpose.
32. As a person who denies location access, I want suburb or postcode entry, so that I can still use the relevant Branches.
33. As a person allowing approximate location, I want nearby search to work where possible, so that precise location is not demanded unnecessarily.
34. As a Participant following an external destination, I want maps, trailers and retailer or Platform pages to open safely, so that I can act on the outcome and return to the Session.
35. As a Buyer, I want the Group Order and Shares preserved through a handoff and return, so that my group can coordinate while payment remains with the Platform.
36. As a Shopper, I want to open a Shopping List from the app or browser even after its Session ends, so that the list remains useful for its own lifetime.
37. As a Shopper, I want Claims to preserve their existing first-tap and release rules, so that all devices see the same shared list.
38. As a person using Cook View, I want current cooking progress recoverable and the screen awake while actively cooking, so that interruptions do not make me lose my place.
39. As a Shopper holding an expired list, I want an accurate expiry message, so that installation does not imply indefinite storage.
40. As a Profile holder, I want to continue signing in with Google, so that I retain access to my existing Friends.
41. As an Apple user, I want a suitable Sign in with Apple option, so that I can authenticate without disclosing my underlying email address.
42. As a Profile holder moving between platforms, I want to access the same Profile and Friendships, so that changing device does not create an accidental second social identity.
43. As a Profile holder linking sign-in providers, I want ownership verified explicitly, so that someone with a similar name cannot take over my Profile.
44. As a Profile holder using Hide My Email, I want Friends discovery to work with my chosen identity, so that privacy does not make the social features unusable.
45. As a person cancelling sign-in, I want to return to a usable app and preserve my guest Session, so that authentication failure does not stop group participation.
46. As a Profile holder, I want to sign out and have privileged access stop appropriately, so that a former session cannot keep using my social identity.
47. As a Profile holder, I want to delete my account from the app, so that I can remove my Profile and associated personal data.
48. As a person who uninstalled the app, I want a public web deletion path, so that I do not need to reinstall to request deletion.
49. As a person deleting my account, I want confirmation, accurate completion status and explained retention, so that I know what was removed and what remains.
50. As a Participant or Profile holder, I want to report abusive visible content or behavior, so that the operator can investigate it.
51. As a Profile holder, I want to block unwanted social interaction, so that the other Profile cannot keep sending Friend Requests or Session Invites.
52. As a guest Participant, I want appropriate Session-level safety controls, so that being a guest does not remove access to reporting and removal protections.
53. As a person using the app, I want accessible privacy, support and usage information, so that I understand its data practices and can get help.
54. As a person using a screen reader, I want meaningful controls, focus and announcements, so that I can complete the primary flows independently.
55. As a person using large text or a small phone, I want reachable controls around the keyboard and system insets, so that important actions are not obscured.
56. As an Android user, I want Back to dismiss overlays or navigate predictably, so that it neither traps me nor silently leaves a Session.
57. As a person sensitive to motion, I want reduced-motion settings respected, so that the app remains comfortable to use.
58. As a beta tester, I want a reproducible build and clear scenarios for reporting failures, so that feedback leads to actionable fixes.
59. As a store reviewer, I want dependable access and instructions for multi-participant and Profile flows, so that I can evaluate the submitted build without operator assistance.
60. As an operator, I want reproducible signed builds with controlled credentials, so that releases can be produced and recovered safely.
61. As an operator, I want an evidence-based release gate covering both stores and all supported clients, so that publication does not rely on a browser-only smoke test.
62. As a person using an older installed version, I want compatible backend behavior or a clear necessary-update path, so that a server deployment does not unexpectedly break the app.
63. As an operator, I want to identify crashes, failed joins, authentication errors and provider costs without logging private capabilities, so that I can maintain the service responsibly.
64. As an operator, I want a defined support, deletion and moderation process, so that public distribution creates manageable ongoing obligations.
65. As a person using the free release, I want no unexpected payment flow or unrelated permission request, so that the product remains focused on deciding together.
66. As a returning Participant with a rejected rejoin capability, I want recovery to fail without changing any Session, so that an old code or removed identity cannot silently grant fresh membership or Host authority.
67. As a Profile holder who blocked someone, I want only my own deliberate unblock action to remove my block, so that unfriend, mutual blocking or a stale invitation cannot bypass it.
68. As a Host facing abusive behavior, I want to remove an online non-Host Participant, so that the current Session can continue with correct membership and outcome calculations.
69. As a Shopper opening a forwarded list after its Session expires, I want reporting and content-blocking controls on that list, so that safety does not depend on ever having been a Participant.
70. As a Shopper concealing an abusive name, I want my Claims, Tally and “Yours” indicators to stay correct, so that content moderation does not change who is shopping for which lines.
71. As a person submitting an abuse report, I want only necessary evidence retained for a stated period, so that reporting does not turn the Session into permanent history.
72. As a store reviewer testing account deletion, I want separate disposable accounts and another complete test run, so that exercising deletion does not lock me out of the rest of the review.

## Implementation Decisions

- **Scope and architecture:** reuse the current React interface, router, state management, shared contracts and Railway services through Capacitor with bundled frontend assets. Retain all four Branches and browser participation. Keep native device integrations small and near existing functional boundaries; no new UI framework, separate user database or backend rewrite.
- **Prototype before expansion:** validate bundled execution on a physical iPhone and Android phone with a browser Participant. Exercise a complete shared Session, HTTP, Socket.IO, streamed Comparison, app background/return, sharing, location and a system-browser authentication callback. Record measured problems and the chosen dependency/toolchain versions before proceeding.
- **Release configuration:** maintain distinct development/staging and production app configurations, stable package identities and an explicit canonical public HTTPS origin. Release builds must reject missing or development service endpoints. Bundle application code rather than loading the live website as the app. Preserve the existing image hosts and legacy Invite Links during rebranding.
- **Native capabilities:** integrate app lifecycle, sharing and foreground geolocation. Introduce keyboard, status-bar or keep-awake integrations only where needed to meet tested behavior. Preserve manual location entry, share cancellation, accessibility, safe areas and deterministic Android Back behavior. Open external content outside the privileged application WebView using validated schemes/destinations.
- **Storage:** add native durable recovery for the minimum valid Session and Cook View progress. Keep authentication, PKCE and rejoin credentials in maintained OS-backed secure storage and non-secret lightweight state in suitable native storage. Preserve browser tab-isolated storage. Do not persist Group Order menus, connection flags or a Session history.
- **Recovery authority:** the server remains authoritative for membership, round, Deck, Submission, Match, Group Order and expiry. Hydrate native recovery before routing or joining, then reconcile before enabling mutations. If a join request carries a rejoin capability, require a match to the current Session and Participant/display name or reject it before any departure, name claim, Host assignment or other state mutation. Never automatically retry as a fresh join without the capability; fresh admission requires a separate deliberate user action. A transient failure preserves recoverable state; a definitive invalid capability, Leave or expiry clears it. Do not blindly replay timed-out mutations.
- **Optional identity during recovery:** refresh Profile authentication without blocking valid guest recovery on Supabase availability. Session authority remains the Participant capability, so ordinary sign-out does not expel that Participant. Refresh or revoke actual social privileges, including any privileged socket behavior, and test existing per-request authentication before inventing a token-denylist service.
- **Existing domain invariants:** preserve unique display names within a Session, the distinction between Disconnect and Leave, the four-Participant limit, collaborative Ready and late-arrival dietary rules, and stable display-name keys for ephemeral client group state. Session state remains in Redis, social data in Supabase, and a Shopping List keeps its separate fixed lifetime.
- **Public link handling:** implement Universal Links and Android App Links for the intended Session, Shopping List/Cook View and authentication routes, with canonical HTTPS shares. Association files must be actual JSON over HTTPS without redirects or challenges, using the correct published signing identities. Validate cold/warm delivery, legacy hosts, malformed input and links received during an existing Session. Preserve browser fallback; do not promise deferred invitation delivery through store installation.
- **Google and Apple identity:** retain Google for existing Profiles and add a compliant Apple sign-in option. Use system-browser OAuth and PKCE where applicable, with validated, deduplicated callbacks and secure verifier persistence. Prefer native Apple sign-in on iOS and permit access to Apple-created Profiles through browser/Android sign-in. Handle relay addresses, missing names, cancellation and provider revocation. Never run Google's authorization screen in the app's embedded WebView.
- **Profile continuity:** keep existing authenticated identifiers and Friendships. Where providers need linking, require an authenticated ownership-verified flow; never merge by display name or guessed email equivalence. Show a Profile holder the address used for exact-email Friends lookup with a deliberate copy action and support Apple relay addresses without requiring the real email.
- **Deletion:** expose account deletion in the app and a public independent web entry. The backend derives the target from verified identity, requires suitable recent authentication, revokes applicable provider/session access and deletes associated Profile/social records. Verify existing cascades instead of replacing them unnecessarily. Prevent previously privileged connections/tokens from retaining social access. Report partial failure and allow safe completion/retry.
- **Data boundaries:** determine which active data is genuinely attributable to a Profile. Guest ownership must never be inferred from a display name. State precisely how shared guest data, locally held capabilities, logs and backups are handled. Add no blanket identity linkage between Profiles and guest Sessions merely to simplify deletion.
- **Profile blocking:** represent independent directional blocks using a timestamp per persisted side of the Friendship pair; enforce that its status is blocked exactly when at least one directional block exists. Either side may block, only its actor may remove that block, and clearing the last block deletes the relationship rather than implicitly restoring friendship. Unfriend, decline or a stale accept cannot clear a block. Invalidate pending Friend Requests and Session Invites in both directions. Serialize block, unblock, request/invite creation, acceptance and unfriend by canonical Profile pair, including when the relationship row does not yet exist, through the existing FriendsStore/database boundary. Retain direct-table denial/RLS. Inspect and conservatively resolve any legacy ownerless blocked state before migration; never guess a blocker or discard protection silently.
- **Participant safety:** require appropriate terms and name validation/filtering, and expose reporting and Session-scoped content muting. Mute by the existing Session Code and unique display name, clear it on Leave/expiry, and change displayed content only, never domain keys, Ready, counts or Match calculations. The actual Host may moderate-remove an online or offline non-Host Participant using the existing Leave cleanup semantics; authorization must strictly require Host status rather than reuse the absent-Host fallback allowed for other actions. Evict the target socket from the Session room, notify it to clear recovery, reject later commands, and broadcast reconciled membership, Lobby/Group Order state and any now-complete Match. Guests can report/mute an abusive Host and Leave; an authorized operator can terminate a Session. Removed capabilities fail strict resume. Fresh disposable identities remain subject to ordinary admission rules and are not permanently identifiable people.
- **Shopper safety:** apply terms/name validation before a Shopper contributes a name, and provide reporting and per-list content muting on an independently shared Shopping List after Session expiry. Local muting and operator remediation conceal abusive labels consistently in rows, summaries and confirmations, without overwriting the identity string used by Claims, Tally membership or the “Yours” check. Preserve exclusive Claims, quantities and the right of any Shopper to release a Claim. Exceptional operator remediation may revoke an abusive list capability with an honest unavailable outcome. Label muting blocks content within its resource, not a verified person across new names/devices; whether these safeguards satisfy the final shipped surface's store requirements remains a release gate.
- **Moderation evidence:** store only deliberately submitted bounded report evidence, such as resource reference/type, reported text, timestamp and optional contact, in an operator-restricted moderation store. Exclude automatic Session snapshots, Dietary Requirements, Selections, Match history and raw authentication/rejoin credentials. Default to expiry 30 days after resolution unless an explicit legal hold applies. Rate-limit report submission and do not fetch arbitrary URLs supplied as evidence. This is a narrow explicit amendment to ADR 0001's ordinary no-trace retention rule and must be documented before implementation; it does not add general Session history or automatic Profile-to-Participant linkage.
- **Privacy and content:** publish privacy/support/deletion information and third-party credits. Complete a data inventory for actual frontend, backend, processors and native dependencies; derive Apple disclosures, SDK privacy manifests, required-reason declarations, Play Data safety and permissions from that inventory and the final binary. Preserve existing content/attribution boundaries and verify rights for native distribution and marketing assets.
- **Networking/security:** configure both HTTP and Socket.IO for the exact tested native and browser origins. Origin checks are not authentication. Keep TLS verification, release debugging disabled, restrictive WebView navigation and a suitable Content Security Policy. Keep server/operator credentials out of distributed bundles and private capabilities out of logs.
- **Installed-client compatibility:** extend the existing additive-deployment contract policy to clients that cannot be updated immediately. Test the oldest supported released contract against new backend versions, including optional fields and new capabilities. Deploy compatible server changes before app changes; any mandatory-update path must be explicit and usable. Avoid speculative whole-API versioning.
- **Availability and cost:** retain current provider access on the backend and existing quotas/deduplication. Reconnection must not create duplicate paid work. Preserve graceful provider/auth failures and evaluate legitimate groups behind shared carrier IPs. Verify actual dependency health before beta/review rather than equating Redis health with complete availability.
- **Build/release:** extend existing workspace and CI practices with native compile checks, signed iOS archives and Android bundles, controlled release credentials, monotonically increasing platform build numbers, artifact provenance and crash symbols. Separate beta distribution from public publication and ordinary web deployment. Store credentials must not be available to untrusted pull requests.
- **Distribution:** start with English and Australia-only availability, phone-first with deliberate supported-device choices. Use TestFlight and Play test tracks, satisfy any applicable account-specific testing requirements, provide working reviewer access outside Australia, and keep dependencies available throughout review. First publication follows beta verification; phased/percentage rollout controls are for subsequent updates.
- **Repeatable reviewer access:** prepare isolated ordinary review Profiles and separate disposable deletion fixtures using the same authentication, authorization, rate limits and business logic as other Profiles. Prove two full review runs from a clean device outside Australia, including a second Profile for Friends, fresh Sessions, deletion and another fixture without operator help. If provider challenges make supplied Google/Apple access unreliable, provide an ordinary visible password sign-in option for pre-provisioned review identities using Supabase, with public password registration disabled. Disclose it in review notes; no hidden route, credential magic or elevated privileges. Validate/replenish only explicitly designated synthetic fixtures before submission, never deleted real accounts. A full demo-mode substitution is conditional on applicable legal/security constraints and prior Apple approval, not a default alternative to credentials.
- **Store artwork:** use fictional Profile, Participant and Shopper information and movie imagery suitable for Apple's 4+ metadata standard independently of the app's age rating. Verify rights, current image dimensions and attribution for the actual listing assets.
- **Operational completion:** assign owners for signing recovery, membership/credential renewal, SDK requirements, moderation, deletion, support, service cost and incident response. A release is complete only when production installs, links, authentication and mixed-client Sessions are verified and the recovery runbook exists.

## Testing Decisions

- **Primary seam, confirmed by the user:** test complete externally observable journeys through the app UI across iOS, Android and browser Participants. A good test proves a meaningful user outcome and its failure behavior; it does not mirror internal method calls, component structure or storage implementation.
- **Existing contract seam:** reuse the current HTTP and Socket.IO application boundaries to verify membership, Ready, round transitions, rejoin, invalid capabilities, Submission/Match outcomes, Group Order mutation semantics and backward compatibility. Existing collaborative-Lobby contract tests already exercise real sockets, HTTP and Redis through a complete round.
- **Social/security seam:** extend the existing Friends HTTP behavior tests for ownership, discovery, blocking and deletion. Include integration evidence with real authentication and database constraints in an isolated environment, because router tests that mock authentication cannot prove revocation, cascade or cross-user safety.
- **Shared frontend prior art:** extend existing Playwright collaborative-Session, Cook, Watch, accessibility and handoff journeys; use existing sharing cancellation and Session expiry/state regressions where targeted negative paths are clearer. Retain existing list Claim and Comparison stream contract coverage.
- **Native proof:** use actual signed/distributed builds on physical iOS and Android devices for app termination, OS permissions, secure persistence, system-browser authentication, share cancellation, external handoffs and verified app-opening links. Browser mobile emulation is insufficient for these behaviors. Start with a repeatable native checklist; automate repeated scenarios when justified.
- **Recovery matrix:** test short lock/unlock, backgrounding beyond the socket recovery window, process kill, network handover, transient server errors, definitive expiry, Restart while absent, unknown mutation outcome and explicit Leave. Verify stable identity, no duplicate work and reconciliation before mutation. A real Socket.IO regression must prove unmatched/revoked credentials and a reused Session Code cannot change a roster, abandon another Session, claim a reserved name or gain Host authority. Verify guest recovery while Supabase is unavailable and guest continuity during ordinary sign-out.
- **Link matrix:** test installed/not installed, cold/warm app, valid/invalid/expired Session Code, Shopping List expiry, legacy host, second Session, repeated delivery and mismatched/hostile callback input. Test published signing fingerprints, not only debug associations.
- **Identity/privacy matrix:** test Google/Apple success and cancellation, relay email, absent name, ownership-verified linking, expired authentication, sign-out, deletion partial failure and attempts with an old token or active connection. Verify required data removal without deleting another Participant's independent data, and check that logs omit credentials and private capabilities.
- **Safety matrix:** exercise independent/mutual blocks, actor-owned unblock, unfriend/decline and old/racing Session Invite accepts, including a race before a Friendship exists. Verify both fast HTTP outcomes and a bounded real-database concurrency check. Verify strict Host-only online removal, no absent-Host privilege substitution, socket eviction and rejected later commands. Exercise a forwarded Shopping List with a Shopper who never participated after the Session has expired, including terms, report receipt, content muting, redaction, unchanged Tally/Claims and exceptional capability revocation. Prove operator-only report access and actual report expiry; policy prose alone is insufficient.
- **Functional matrix:** complete two- and four-Participant mixed-client Sessions across all four Branches with guests and Profiles. Include dietary conflict, changing Ready, all-pass Submission, late arrival, fifth-Participant rejection, Host absence, Undo, Restart, Group Order handoff, Shopping List Claim/release and Cook View progress.
- **Accessibility and device matrix:** verify VoiceOver/TalkBack, non-gesture controls, large text, keyboard obstruction, safe areas, reduced motion, Android Back, current devices and the oldest supported runtime environments. Test larger device families whenever enabled for distribution.
- **Release gate:** require recorded passes for all mandatory scenarios, no known ownership/data-loss errors, broken primary access, crashes blocking core flows or unfulfilled store policy requirements. Target at least 20 completed mixed-client beta Sessions across the Branches; this does not replace any store-mandated tester count/duration. Set reference devices and performance thresholds after the prototype and retain repeatable measurements.
- **Review-access evidence:** demonstrate two complete reviewer runs including account deletion, replenish only designated synthetic fixtures, and check current screenshot suitability/fictional data before submission. A supplementary video does not replace working access.

## Out of Scope

- Paid downloads, subscriptions, in-app digital purchases, advertising/tracking and monetization infrastructure.
- In-app restaurant booking, grocery/Platform checkout, payment collection, settlement, stored Platform credentials or film streaming.
- Contacts import, camera/microphone/photo-library access, background location and unrelated permissions.
- Push notifications, widgets, watch apps and a tablet-specific redesign; larger-screen usability still applies to enabled device families.
- Full offline catalogues, offline mutation queues, background sockets, conflict-resolution machinery or indefinite Session/Shopping List history.
- Automatic transfer of guest identity between browser and app, or guaranteed invitation transfer through app installation.
- A React Native rewrite, separate Swift/Kotlin product implementations, a new backend, premature multi-region scaling or a new paid build platform without demonstrated need.
- Remote application-code update infrastructure, a moderation dashboard, or permanent cross-Session identification of disposable guests.
- Renaming internal packages, historical ADRs, provider projects or established image hosts solely for the public rebrand.

## Further Notes

- Scope confirmed with the user: **free, Australia first**. Heykeen is the working public name; final domain/name ownership, developer legal entity, account status, supported-device details and access credentials are implementation prerequisites, not facts already verified.
- Two independent reviewers approved this specification after revisions. Testing through mixed-client journeys, existing HTTP/Socket.IO contracts and signed real-device checks was confirmed by the user. The specification incorporates strict resume rejection, directional blocking/concurrency, explicit Participant and independent-Shopper safeguards, narrow report retention, repeatable reviewer access and corrected store-artwork/demo-mode requirements from those reviews.
- Sequence: establish account/domain/toolchain readiness; prove both physical platforms; implement native links/UX and recovery; complete identity, deletion and safety; establish signed delivery; run mixed-client beta; submit and verify launch. Begin enrollment and tester recruitment early because these have external lead times.
- Initial estimate: **31–46 engineering days before contingency**, approximately **8–12 working weeks with reserve**, with enrollment and review potentially extending elapsed time. Re-estimate after the prototype and detailed safety/deletion design; directional blocks, Shopper remediation, report-retention changes and reviewer access can expand the original allowance. This is not an approved spend or delivery guarantee.
- Known enrollment fees are Apple **US$99/year** and Google Play **US$25 once**, subject to local checkout/taxes; infrastructure, hardware and labor are additional. [Apple enrollment](https://developer.apple.com/help/account/membership/program-enrollment), [Google registration](https://support.google.com/googleplay/android-developer/answer/6112435).

[Apple submission requirements](https://developer.apple.com/news/?id=ueeok6yw), [Google target API requirements](https://support.google.com/googleplay/android-developer/answer/11926878).

Explicitly amend ADR 0001 only for deliberately submitted, access-restricted and time-bounded moderation evidence, and extend ADR 0007 for supported installed clients before implementing those changes.
- Policy references for the reviewed requirements: [Apple review and metadata guidelines](https://developer.apple.com/app-store/review/guidelines/), [Google reusable review access](https://support.google.com/googleplay/android-developer/answer/15748846), [Google user-generated content rules](https://support.google.com/googleplay/android-developer/answer/9876937).
